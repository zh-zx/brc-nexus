# BRC v2 — 备份与恢复演练手册（runbook）

> 适用范围：BRC 种质库正式投产后的数据安全例行演练。
> 目标：确认「备份可救、恢复可回、留痕可查」，演练周期建议每月一次（见第 5 节）。

## 0. 数据与文件位置

| 对象 | 路径（相对 server/） |
| --- | --- |
| 主库 | `data/brc.db`（+ WAL 临时文件 `brc.db-wal` / `brc.db-shm`） |
| 自动/手动备份 | `data/backups/brc-backup-*.db`、`brc-backup-manual-*.db` |
| 恢复留底 | `data/backups/pre-restore-*.db` |
| 恢复进程外日志 | `data/restore.log`（恢复不随数据库回退，可追溯） |
| 待恢复标记 | `data/.restore-pending.json`（启动时消费，正常情况不存在） |

备份文件是**单文件一致性快照**（`VACUUM INTO`），可直接被恢复流程接受。

## 1. 手动作备份（日常）

- 界面：设置 → 数据安全 → 手动备份；或 API `POST /api/dbadmin/backup`（仅 admin）。
- 自动备份：设置 `backup.enabled=true`、`backup.interval_hours`（默认 24h）、`backup.retention_days`（默认 30 天自动清理）。
- 建议：重要操作（改种质字典、批量导入、上线变更）前手动备份一次。

## 2. 恢复流程（演练/灾难恢复）

恢复分两阶段，**绝不就地覆盖正在运行的库**：

1. **排入恢复**（运行时，当前库不受影响）：
   - 界面：设置 → 数据安全 → 选择一个备份 → 「恢复」；或 API：
     `POST /api/dbadmin/restore`，body `{ "filename": "brc-backup-xxx.db", "confirm": true }`（仅 admin，需二次确认）。
   - 服务端校验：文件名裸名（防路径穿越）、文件存在、≥512 字节、SQLite 魔数合法。不合法即拒绝，不写标记。
   - 成功后：写入 `data/.restore-pending.json`，界面提示「重启服务器以生效」。

2. **重启生效**（应用恢复）：
   - 停止 → 重新启动服务器。
   - 启动时、`initDb()` 之前：自动读标记 →
     a) 先把**当前** `brc.db` 复制为 `data/backups/pre-restore-<时间戳>.db`（恢复本身可回退）；
     b) 用所选备份**原子替换** `brc.db`，并清除残留 `-wal`/`-shm`（防旧日志串染新库）；
     c) 删除标记；在 `data/restore.log` 追加 `RESTORE ...` 一行（含操作者/备份名/留底名）。
   - 控制台启动日志会打印 `[restore] 已从备份 ... 恢复（留底：...）`。

3. **验证恢复结果**：
   - 登录系统 → 确认关键数据（种质数、最近操作、审计日志时间线）与备份时间点一致；
   - `/api/health` 无完整性告警（`integrity` 正常、`orphans` 为空）；
   - 若恢复后发现问题：可用留底 `pre-restore-*.db` 再走一次恢复回到恢复前状态。

### 注意事项（重要）

- **排入恢复后到重启之间**系统仍会正常写入；重启时留底会保留该窗口的最终状态，但恢复本身回退到所选备份。
- **预留时间**：排入恢复后请尽快重启，避免操作者以为已恢复、实际未生效。
- 若误删了标记或备份缺失：启动时会自动「取消恢复」并保留当前库原样（`[restore] 恢复取消：...`），不破坏数据。
- 恢复是**连同审计日志一起回退**的整库回滚；跨备份点的事后追责以 `data/restore.log` + 备份文件为准。

## 3. 自动化对账（P0 加固后的孤儿清理）

每次启动时 `/api/health` 自带完整性自检；若出现 `orphans: [...]` 告警：

```bash
cd server
node scripts/reconcile-orphans.mjs            # 只读报告每条孤儿 + 拟定动作
node scripts/reconcile-orphans.mjs --apply    # 备份留底后按策略清理（建议先停服）
```

清理策略：无属主令牌→撤销、孤儿库存→归入「待归属 / UNASSIGNED」、孤儿明细→删除；不可自动的部分只报告不破坏。

## 4. 演练检查表（一次完整演练）

- [ ] 做一次手动备份 → `data/backups/` 出现新文件
- [ ] 记录一个可识别的测试变更（如新增一个测试种质）
- [ ] 排入恢复（选演练开始时的备份）→ 提示「重启生效」
- [ ] 重启服务器 → 控制台出现 `[restore] 已从备份 ... 恢复`
- [ ] 登录确认：测试变更已消失、库存/审计回到备份点
- [ ] 确认 `pre-restore-*.db` 已生成、`restore.log` 有新 `RESTORE` 行、`brc.db-wal` 已重建为正常
- [ ] 收尾：删除演练期间产生的测试数据，确认 `/api/health` 无告警

## 5. 建议频率

- 月度：§4 全套演练一次。
- 变更期间：升级版本 / 改性状字典 / 批量导入后，手动备份并抽查一次恢复入口。

> 安全提示：备份/恢复端点均仅 admin 可用；请勿将 `data/` 目录对外暴露。
